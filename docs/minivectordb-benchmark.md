# MiniVectorDB 性能记录（自测，非官方平台成绩）

> **重要说明**：本文件中的全部数字都是在本机和自建服务器上自测得到的，**不是官方
> 平台的评测结果**。官方成绩以平台对锁定 commit 的评测为准。平台的基线数值、cgroup
> 统计口径与三轮测量规则均未公开，因此本文只用于说明量级与取舍，不能用来推断排名。

## 1. 测试方法

脚本：`minivectordb/benchmark/benchmark.py`，形状对齐赛题第 3.3 节：

- 写入：10,000 条记录，128 维向量，每批 100 条提交，共 100 批；
- 查询：1,000 条 TopK 查询，K = 10，其中一半带普通列等值过滤；
- 查询在数据装载与索引准备（容器重启、启动时重建索引）之后执行；
- 召回率用 `exact` 模式的返回集合作为真值，按过滤组与不过滤组分别统计；
- 峰值内存与磁盘 I/O 读取容器 cgroup 的 `memory.peak` 与 `io.stat`，与赛题的统计
  口径一致。

```bash
python3 minivectordb/benchmark/benchmark.py --image minivectordb:latest
```

## 2. 结果

| 指标 | 服务器（Ubuntu 24.04，2 vCPU，约 2 GiB） | 本地（Windows + Docker Desktop） |
| --- | ---: | ---: |
| 写入 10,000 行 | **2.432 ~ 2.545 s** | 3.515 s |
| 干净关闭落盘 | 0.149 ~ 0.152 s | 0.172 s |
| 启动时重建向量索引 | 1.505 ~ 1.676 s | 1.611 s |
| 查询 1,000 次（`ann`） | **1.889 ~ 2.084 s** | 3.719 s |
| 查询 1,000 次（`exact`，作为参照） | 1.946 ~ 1.956 s | 3.643 s |
| 平均 Recall@10 | 1.0 | 1.0 |
| 平均 Recall@10（带过滤） | 1.0 | 1.0 |
| 平均 Recall@10（不过滤） | 1.0 | 1.0 |
| 写阶段峰值内存 | 33.0 MiB | 33.0 MiB |
| 查询阶段峰值内存 | 20.5 ~ 20.6 MiB | 21.0 MiB |
| 写阶段磁盘写入 | 6,246,400 B | 6,246,400 B |
| 查询阶段磁盘读写 | 0 B / 0 B | 0 B / 0 B |

区间是同一份代码在服务器上重复测量的波动范围（服务器是共享的云主机，查询耗时会随
邻居负载浮动），不是一个稳定值。

本地的查询数字明显更大，是因为 Windows 宿主机与 Linux 虚拟机之间的 docker CLI 管道
转发每条消息要额外付出约 1.3 ms（详见验证记录第 4 节）。两套环境的绝对耗时不可互相
搬用。

服务器上 `fdatasync` 的实测延迟为 0.72 ms（4 KiB）/ 0.97 ms（64 KiB），100 次提交
的持久化开销不到 0.1 s，因此写阶段的主要成本是数据编码、索引维护与 WAL 写入。

## 3. 查询耗时分解（服务器）

用 `profile_queries.py` 分别测量同一张 10,000 行表上的不同查询形态：

| 查询形态 | 耗时 |
| --- | ---: |
| 普通扫描，不算距离 | 0.561 ms/次 |
| 普通扫描，带等值过滤 | 0.591 ms/次 |
| 距离 + 过滤（`exact`） | 0.779 ms/次 |
| 距离 + 过滤（`ann`） | 0.821 ms/次 |
| 距离，无过滤（`exact`） | 1.365 ms/次 |
| 距离，无过滤（`ann`） | 1.495 ms/次 |

可以看出：

- `exact` 路径要读完整个表（10,000 行 × 128 维 × 4 B ≈ 5 MiB 向量载荷），是访存
  带宽受限；
- `ann` 路径只读候选集，但 HNSW 的图遍历是随机访存，在 128 维、10,000 点的规模上
  两者接近。数据量再大一些时 `ann` 的优势才会显现；
- 过滤本身很便宜（0.03 ms 量级），过滤会缩小 `ann` 的候选集，所以带过滤时 `ann`
  与 `exact` 的差距更小。

## 4. 优化过程与取舍

按时间顺序记录，每一项都先测量再改：

1. **排序键扁平化 + 部分选择**：原来是每行一个 `std::vector<SortKey>`，扫描一万行
   就有一万次堆分配；排序也用全量 `std::sort`。改成排序键放在一个扁平数组里，
   并在有 LIMIT 时用 `nth_element` 只选出前 K 行。
2. **候选按页分组处理**：`ann` 路径原来对每个候选做一次「按主键查找 + 钉住页」，
   一次查询要钉住几百次页。改成先按页分组，一页只钉一次。
3. **自适应候选预算**：`ann` 原本固定取 256 个候选（图遍历的 ef 也被抬到 256）。
   改成从 `max(4K, 64)` 起步，只有当过滤把候选吃光时才按 4 倍递增。
4. **HNSW 容量按倍数增长**：这是最大的一项。原先 `ensure_node_slots()` 把容量正好
   预留成「节点数 + 1」，导致每次插入都重新分配并整体拷贝向量库，插入退化成平方
   复杂度。修复后带向量插入从 1.758 ms/行降到 0.290 ms/行，写阶段从 18.06 s 降到
   2.43 s。

没有做的取舍：把向量索引改成「写入时只打标记、查询前再整体重建」。这样写阶段可以
再快一个数量级，但一旦平台的查询与写入交错，第一次近似查询就要付出一次全量重建，
最坏情况比现在的实现慢得多。因为召回率与功能准入是硬门槛，所以保留增量维护。

## 5. 复现

```bash
docker build -t minivectordb:latest .
python3 minivectordb/benchmark/benchmark.py --image minivectordb:latest
```

脚本自带随机种子（`--seed`，默认 20261113），默认参数与赛题描述的规模一致。
